문제 해결

먼저 san doctor 를 돌린다

섹션 제목: “먼저 san doctor 를 돌린다”

무엇이 잘못됐는지 모르겠으면 san doctor 부터 돌린다. 원인일 가능성이 큰 것부터 — 설정 → 레포 → 도구 → 설치 → 상태 — 순서로 보고, 문제마다 고치는 명령(또는 파일:줄)을 붙인다. 읽기만 한다: 파일을 고치지 않고, 작업자를 띄우지 않고, 토큰을 출력하지 않는다.

✗ 가 하나라도 있으면 종료 1, ⚠ 만 있으면 0. 오케스트레이터 레포 밖에서 부르면 도구 · 설치만 본다. 다른 명령이 설정 문제로 멈출 때도 오류 끝에 — 원인 찾기: san doctor 가 붙는다.

예시 출력(경로는 바꿨다) — 접두사가 겹치고, 지워진 워크트리가 RUNNING 으로 남아 있다:

gh 계정 · 권한

섹션 제목: “gh 계정 · 권한”

증상: san self-update 가 gh 로그인이 없다 — gh auth login … 또는 gh release download 실패 — 판 · 권한 … 을 확인한다 로 멈춘다.

  • 보일러플레이트 레포는 비공개다. 그 레포를 읽을 수 있는 계정이 gh 에 로그인돼 있어야 한다: gh auth status.
  • 활성 계정이 다르면 그 계정을 더하고(gh auth login) SAN_GH_USER=<계정> 으로 부른다. 기본은 SAN_REPO 의 주인 계정이다.
  • 없는 판을 달라고 했는지 본다: san self-update --version v<판>.
  • gh 자체가 없으면 gh 가 없다 — … 로 멈춘다 — gh 를 설치한다.

sha256 이 맞지 않는다

섹션 제목: “sha256 이 맞지 않는다”

증상: sha256 이 맞지 않는다 — 설치하지 않는다. 받은 압축본이 깨졌거나 바뀌었다. 다시 받는다. 계속되면 릴리스 파일을 관리자에게 알린다. 확인 없이 설치하는 옵션은 없다.

오케스트레이터 레포 안이 아니다

섹션 제목: “오케스트레이터 레포 안이 아니다”

증상: 오케스트레이터 레포 안이 아니다 (…) — config/repos.env · scripts/common.sh 가 있는 폴더나 그 아래에서 부른다. san status · san dispatch 같은 명령은 오케스트레이터 레포(또는 그 하위 폴더)에서 부른다. 새로 만들려면 san new <폴더>. san new · san self-update · san version · san gate 는 어디서나 된다.

아직 init 전이다

섹션 제목: “아직 init 전이다”

증상: 아직 init 전이다 — 먼저 ./scripts/init.sh 를 돌린다. san init --name … --repo … 를 돌린다. 이미 init 했는데 다시 하려면 --force(설정 · CLAUDE.md · 계약서 틀을 새로 쓴다). 레포만 바꾸려면 san repo add|set|rm.

종료 9 — 작업자 상한

섹션 제목: “종료 9 — 작업자 상한”

증상: san dispatch 가 상한 — 지금 RUNNING N개 · 상한 M개. <ID> 는 보내지 않았다(실패 아님) 를 찍고 종료 9. MAX_ACTIVE_WORKERS 만큼 이미 일하고 있다. 앞 작업자가 끝나면(VALIDATION · BLOCKED) 다시 보낸다. 상한을 바꾸려면 config/workers.local.env 또는 환경변수 MAX_ACTIVE_WORKERS — 작업자. runtime/state.json 에 이미 끝난 작업이 RUNNING 으로 남아 있으면 san await <ID> 로 사건을 받아 상태를 갱신한다.

게이트 대조 실패 · 지문 불일치

섹션 제목: “게이트 대조 실패 · 지문 불일치”

증상: san land 가 게이트 기록이 없다 · 게이트 기록이 「실패」다 · 게이트 뒤에 코드가 바뀌었다(지문 불일치) 로 멈춘다.

  • 작업자 워크트리에서 게이트를 다시 돌린다: san gate --base origin/<branch>(시험이 필요 없는 변경이면 --waive-tests "이유").
  • 검토하면서 중앙이 워크트리 파일을 고쳤어도 지문이 바뀐다 — 게이트를 다시 돌린다.
  • 중앙이 직접 확인했으면 san land <ID> --skip-gate(경고가 남는다).

게이트

게이트가 시험이 없다고 실패한다

섹션 제목: “게이트가 시험이 없다고 실패한다”

증상: 시험 아닌 소스가 바뀌었는데 새 시험 함수도, 기존 시험에 더한 단언도 없다. 시험을 더하거나 기존 시험에 단언을 더한다. 문서 · 문구 · 스타일만 바꿨으면 --waive-tests "이유". 자리표시 시험(skip/only/todo)을 새로 넣었다 면 그 skip · .only 를 지운다.

worker-start 실패

섹션 제목: “worker-start 실패”

증상: worker-start 실패(rc=…) — 다시 띄우지 않는다. 영수증: runtime/<ID>.worker-start.json · .err. 다시 띄우지 않는다. 먼저 영수증 runtime/<ID>.worker-start.json · .err 를 읽고 원인을 고친다. 복구 안내:

워크트리를 만들 수 없다

섹션 제목: “워크트리를 만들 수 없다”
  • origin/<branch> 을 받지 못했다 — 레포에 첫 커밋과 origin 이 있어야 한다.
  • Orca 에 등록되지 않은 레포 — orca repo add --path '<경로>' </dev/null.
  • Orca 가 이 레포를 git 이 아닌 'folder' 로 등록했다 — 첫 커밋 전에 등록하면 이렇게 된다. 출력에 나온 orca project setup-existing-folder … --kind git 명령으로 고친다.
  • Orca 가 별도 워크트리가 아닌 본 체크아웃을 내줬다 — 위와 같은 원인이다. 작업자를 띄우지 않았다.

작업자가 멈춘 것 같다

섹션 제목: “작업자가 멈춘 것 같다”

san await 가 stale 로 끝났으면 작업자 화면이 AWAIT_STALE_MIN 분 그대로다 — 권한 창이나 셸 프롬프트에서 멈췄는지 본다: orca terminal read --terminal <handle> </dev/null. timeout(종료 124)이면 사건 없이 AWAIT_TIMEOUT_MIN 분이 지났다 — 터미널을 직접 보고 필요하면 san await 를 다시 띄운다.

land 가 푸시하지 않았다

섹션 제목: “land 가 푸시하지 않았다”
  • rebase 충돌 — 워크트리에서 직접 풀거나 새 계약서로 다시 보낸다.
  • 검증 실패 — runtime/<ID>.verify.log 를 본다.
  • 검증이 추적 파일을 바꿨다 — 바뀐 것을 보고 커밋할지 되돌릴지 정한다.
  • 올릴 커밋이 없다 — 워크트리에 변경이 없다.
  • <ID> 는 아직 RUNNING — 작업자가 끝난 뒤(san await) 부른다.

zsh 에서 명령이 이상하다

섹션 제목: “zsh 에서 명령이 이상하다”

기본 셸이 zsh 이면: 따옴표 없는 변수는 쪼개지지 않는다(bash -c 로), 맞는 glob 이 없으면 오류(nomatch), ===== 처럼 = 로 시작하는 낱말은 명령 경로로 바뀐다, 변수 이름 status 는 읽기 전용이다. orca … 는 stdin 을 먹으니 </dev/null 을 붙인다. pkill -f 는 쓰지 않는다.
